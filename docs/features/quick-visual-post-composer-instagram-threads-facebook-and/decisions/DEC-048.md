## Context

REQ-006 asks for the result of the check 'does an approved post with one picture and a caption already go out correctly' to be recorded per platform, with the code path (criterion 1), and for only the gaps to be filled (DEC-044, F-001). The check was made on the code and with automated end-to-end tests against a stand-in post form (src/core/pipeline/quick-post-send.test.ts: the real gate, authority and browser toolbox, one test set for each of Instagram, Threads and Facebook). The real sites were not touched: no real account is used by tests.

## Alternatives

1. Rework the AI-browser sending path for the three platforms (rejected: the check shows it already carries one picture and the exact caption, DEC-044 says not to rework what works)
2. Leave the quick post judged only by its connector at the press (rejected: the owner would find out at the site, after the dialog was opened, which lesson 239 forbids)

## Decision

For Instagram, Threads and Facebook an approved quick post (one library picture plus a plain caption) already goes out through the existing path: these are channels the app cannot read (channel.reads false), so sendWays gives noConnector and chooseExecutor returns ai_browser (src/core/pipeline/send-ways.ts); the mission authority checks the content against the approval (mission-publisher.ts), the browser toolbox attaches the one approved file and types the caption, reads it back and presses (src/core/browser-agent/toolbox.ts attach/submit); the approval hash already binds the caption and the picture (name and sha256). That part is not reworked. The gap found: Approve, the gate and the group view judged platform fit (caption limit, picture rules) only for Markdown drafts, and a quick post is stored as plain text, so a too-long Threads caption or an Instagram picture of an unsupported shape passed Approve and failed on the site. Fix: one function, judgedForFit / sendFitProblems, that Approve, the gate, the group view and the preview all ask; the per-platform picture rules (type, size, shape) are one table in src/shared/post-pictures.ts. Limits used: caption Instagram 2200, Threads 500, Facebook 63206 characters; picture Instagram PNG/JPEG up to 8 MB with width:height between 4:5 and 1.91:1, Threads PNG/JPEG up to 8 MB with ratio between 1:10 and 10:1, Facebook PNG/JPEG/GIF. The three card shapes (1080x1080, 1080x1350, 1080x566) pass on every platform. Also: the file-chooser guard of the AI browser now catches the 'Add photos/videos' form of Facebook, so the AI cannot open a native dialog nobody answers. Each platform has an automated end-to-end test (approve, send way, mission carries the approved file once and the exact caption; an edited caption or picture sends nothing until approved again; scheduled or automatic sends are refused with words).

## Reason

REQ-006 and DEC-044 require the result of the check per platform to be recorded and only the gaps to be filled. The limits come from public size guides and Meta's Threads API documentation, not from the real post forms, so they are an assumption until a live try; each is a one-line edit of the table. The real Instagram, Threads and Facebook post forms were not exercised.

## Consequences

Real-site behaviour stays unproven (issue #8 is the place for the live checklist): the real post forms of the three platforms, the accepted types/sizes/ratios, Instagram's Create menu role, Facebook's 'Add photos/videos' label, typing of # and @ into the caption field. Instagram's 30-hashtag limit is not implemented. The decision is proposed: accepting it is the owner's.
