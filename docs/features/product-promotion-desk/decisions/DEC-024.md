## Context

DEC-018 runs the account missions (sign-up, profile) with full access for the engine, like MarkView. Stream B1 adds a mission that publishes an owner-approved post or reply in the account's own browser. The send ticket (DEC-008, REQ-004) is a real boundary only on the MCP path: `browser_submit` is the one tool that can press a publishing control, and it needs the gate's ticket. An engine that also has a shell, file tools and web tools can be steered by a page's text (prompt injection) to act around the ticket. An independent security review of B1 rated this high. The owner accepted the finding on 2026-11-14.

## Alternatives

1. Keep full access in the post mission, with the ticket as the only barrier (DEC-018 as it is): rejected for publishing, the ticket would not bind an engine that can act outside the toolbox
2. Restrict Codex as well: not possible with Codex 0.169, no switch removes its shell or file tools, and its sandbox limits what a command may change, not what it may run or read
3. An allow-list with `--permission-mode dontAsk` but built-in tools left on: rejected, in a real probe `ls` and a file read still ran; only `--tools ""` removed the tools

## Decision

In a post mission (label `agent.post`) Claude Code is started with `--tools "" --permission-mode dontAsk --allowedTools mcp__<server>` together with `--strict-mcp-config --mcp-config`, and without `--dangerously-skip-permissions`, so the only tools it has are the application's own browser tools. A post mission with Codex is refused with a message the owner sees (`engine_cannot_confine`), and the connector stays the way to publish with Codex. The sign-up and profile missions and the interactive agent sessions are unchanged: DEC-018 stands for them. The flags and the port flag `confinesAgent` change together.

## Reason

The owner's rule is that an instruction to the model is never what authorizes a publication; that holds only if the model has no other way to publish. Confining the engine to the toolbox makes the ticket and the page guards the only path. The flags were checked against `claude --help` (2.1.325) and by a real run in an empty folder with a stand-in MCP server: the built-in tools were absent and the MCP tool worked.

## Consequences

Publishing through the AI browser works with Claude Code only; with Codex the owner uses the connector. The confinement rests on command-line flags and is not verified at run time: `--output-format stream-json --verbose` gives a `system/init` event that lists the tools and could be checked, and `--setting-sources` is not pinned, so the owner's own Claude settings (hooks, plugins) still load. Re-check the flags when the CLI is upgraded. The setting `publishWith` stays `connector` by default and has no control in the interface yet; a live acceptance with the owner at the keyboard comes before it is ever set to `ai_browser`.
