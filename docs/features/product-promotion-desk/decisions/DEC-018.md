## Context

DEC-017 ran a round loop in the application: snapshot, a text-only engine answers with steps, the application carries them out. The owner rejected it: it is not how MarkView does it, the engine must hold the goal itself (create an account: invent the name and surname, fill in, look at the result, ask the person for a CAPTCHA, go on). The owner told us to read MarkView's code: there the real Claude Code / Codex runs with the app's MCP server in its own launch arguments and with full access. On 2026-11-08 the owner approved node-pty, xterm.js and any native module, and full access for the engines; then said no screen is needed: questions are a pop-up, and the work is a short, concrete goal (fill everything in and make sure the account exists).

## Alternatives

- A text-only engine answering one round at a time (DEC-017): rejected by the owner, the application holds the goal and the engine cannot work on its own
- A visible terminal (node-pty + xterm.js) with the person typing to the AI: approved by the owner, then not needed: they want no screen, questions as a pop-up and a short concrete goal
- Engines limited to the app's tools only (no shell): rejected by the owner, they get full access like in MarkView

## Decision

An account mission (first: sign-up) is given as a GOAL to the real Claude Code or Codex CLI, run in the background with full access (--dangerously-skip-permissions; --dangerously-bypass-approvals-and-sandbox) and the app's MCP server in its own launch arguments (Claude --mcp-config with --strict-mcp-config; Codex -c mcp_servers.* with --ignore-user-config). The engine works the goal itself by calling tools until it reports a result. The MCP server is the app binary run without UI (ELECTRON_RUN_AS_NODE), relaying over a Unix socket (mode 0600, token per run) to the app, which performs each call in the account's own browser. Tools: MarkView's browser set (snapshot with element refs, navigate, click, type, select, press_key, evaluate, screenshot, wait_for) plus ask_owner (a pop-up in the app; the AI waits for the answer), note_value and report_result. A password is written as {{PASSWORD}} and typed by the application. No terminal and no new screen: progress appears in the account's existing panel, questions in a pop-up. Control, Stop and the owner's takeover keep working through the existing controlled session. After the engine ends, the site's own login check decides whether the account exists. Publishing from an account stays owner-approved through connectors and tickets. The round loop of DEC-017 is removed once this path passes.

## Reason

It matches the model the owner works with in MarkView and what they asked for: the AI owns the goal and works for a long time, and the person can step in. A loop run by the application was the wrong owner of the goal.

## Consequences

No new libraries. Engines act with full access, so a page's text is no longer kept away from a tool-using engine; the password stays out of the transcript and log by {{PASSWORD}}; the server keeps host and ref checks as sanity rules, not as a security boundary. A run costs the owner's subscription (Codex was at 18% of its weekly limit). The 0.4.0 plan/agent round loop and the tool-free requirement for starting the agent are removed; snapshot.ts and pageStep stay as the tool executor.
