## Context

Threads (and Instagram) take a picture or a video through their API only from an address on the internet; a desktop application has none. D5 of the publishing plan chose "a storage bucket of the owner's own; the file is uploaded before the send and deleted after the platform has read it". Until 0.83.0 a Threads account that works through the API refused every post with a picture or a video.

## Alternatives

1. A public bucket with plain addresses: simpler, but every file is readable by anyone who guesses its name for as long as it stands
2. A hosting service run for all owners: the owner's pictures would pass through a server of ours, against the application being local
3. A tunnel from the internet to this Mac for the minutes of a send: needs a third-party service and an open door into the computer
4. Keep refusing pictures on API accounts and send them only in the account's browser: leaves Threads without scheduled picture posts and makes the Instagram API impossible

## Decision

Settings has a card "A place for files": the address of the store, the region, the bucket, the access key id, and the secret access key, which goes to the keychain vault and is never shown or logged. The application speaks the S3 API, which Amazon S3, Cloudflare R2, Backblaze B2 and others share, with its own signing (AWS Signature Version 4, node:crypto, no new library). For a send it puts each file into the bucket under ppd/<id>/<name>, gives the platform an address signed for one hour (the bucket stays private), and deletes the file when the send ends, whatever its end. "Check the place" puts a small file, reads it through its signed address as a platform would, and deletes it. A connector asks for the place through ConnectorContext.publicFiles(); it is given only to an account that works through an API. Threads through its API now carries one picture (JPEG, PNG), one video (MP4, MOV) or up to 20 of them as one post; a video is waited for up to five minutes. With no place saved, the editor says so before the owner approves and the send refuses before anything is asked of Threads.

## Reason

It is the default the plan already took (D5), it keeps the owner's files in the owner's own account with no service of ours in between, and the S3 API makes one implementation serve every common store. A signed address that expires keeps the bucket private, so nothing is public beyond the hour of a send. Signing is forty lines of a documented algorithm, tested against the examples of Amazon's own documentation, so no library is added.

## Consequences

The owner needs a bucket and an access key that may put, read and delete in it. Unproven with a real store and a real platform: nothing was tried against Amazon S3, R2 or B2, and whether Threads reads a file from an address with a signature in its query is not said in Meta's pages (they say only that the file must be on a public server). A file the store refuses to delete stays in the bucket; its address stops working within the hour, and the log says so. The Instagram API (phase H) can now be built on the same place.
