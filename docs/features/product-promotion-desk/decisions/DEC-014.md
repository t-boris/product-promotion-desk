## Context

DEC-008 and REQ-010 say the application neither requests nor stores credentials and that sign-in happens on the site's own page. The owner (2026-11-08) mostly creates new accounts and asks for an account manager that keeps the passwords, signs in by itself, suggests or makes an e-mail address for a new account, reads that mailbox, and (later the same day) shows in one reader every message that concerns the business, for every account, with a button to open a message in the browser.

## Alternatives

1. Keep the rule: no credentials stored; sign in by hand each time. Safest, but the owner asked for automatic sign-in.
2. Use the owner's own password manager (1Password or the browser's) for sign-in: nothing stored here, but it depends on a third party that cannot be checked from the application.
3. Create mailboxes and platform accounts completely automatically: refused, it needs getting around CAPTCHA and phone verification.

## Decision

The application may store the passwords of the owner's platform accounts and mailboxes, and use them to sign in. This replaces the earlier rule "no credentials are requested or stored by the assistant" (DEC-008, REQ-010) and nothing else in those records. Passwords live only in a vault encrypted with the operating system's keychain (Electron safeStorage) in a file of their own: never in the database, logs, events, the loopback web API, AI prompts, backups or exports. They are used only to fill the sign-in or sign-up page of the account's own browser, on a page that belongs to the platform, with one automatic attempt per account per hour. A CAPTCHA, a second factor, a phone check or a changed page stops the automation and hands control to the owner. The application does not create mailboxes or platform accounts by itself: for a new account it proposes an address (an alias of a connected mailbox or an address on the owner's own domain), generates a password, fills in the sign-up form and lets the owner pass every check. Mailboxes are connected read only, through IMAP with an application password: the application never sends, deletes, moves or marks a message. One inbox shows the messages that concern the owner's accounts (addressed to an address the application proposed for an account, or sent from a platform the owner has an account on), not the rest of the mailbox. Only headers and a short preview are stored in the database; the full text is fetched when a message is opened and is shown as plain text, with no images or remote content, and a button opens the message in the owner's own mail service. A verification code or link is shown next to the account being created and a link is opened only when the owner presses it. Mail text is data and never reaches the AI. Delivered in three releases: 0.2.0 vault and sign-in, 0.3.0 mailboxes and the inbox, 0.4.0 sign-up assistant.

## Reason

The owner mostly creates new accounts and wants one place that keeps the logins, signs in by itself, suggests an address for a new account and reads that mailbox. Storing credentials is the only way to sign in without the owner each time; the keychain is the safest place on this machine. Creating mailboxes and accounts automatically would mean getting around CAPTCHA and phone checks, which platforms treat as abuse and which gets accounts banned, so it is not part of this decision.

## Consequences

New port SecretStore (core stays free of Electron). Migration 204 (accounts.login_name, accounts.last_login_attempt_at), later 205 (mailboxes) and 206 (mail_messages: headers and preview only). The vault is bound to this Mac's keychain and is not in backups: a new machine needs the passwords typed again. Sign-in is the one write-class page operation that needs no SendTicket (REQ-004): it publishes nothing, only the vault service reaches it, and the page itself refuses anything but a top-level https page on the platform's own hosts. Keychain check of 2026-11-08 on this Mac: the app is ad-hoc signed and the deploy script signs it again, so its signature changes with every build; a build with a different signature opened the vault without a prompt and without a delay. macOS may still ask for keychain access in other situations (a locked keychain, a different user); if it does, 'Always Allow' settles it, and a master password remains the fallback if updates keep asking. Outlook/Hotmail personal mailboxes are not supported (OAuth only). Release 0.3.0 adds imapflow (approved) and, to read message text, a mail parser such as mailparser, which still needs the owner's approval before it is added. A stored preview of a message can still contain a code: the database is not encrypted, so previews drop codes and links. The mail service's own address for "open in browser" is known for Gmail (a direct link by message id) and given by the owner for the others.
